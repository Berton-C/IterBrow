## Contract statement

IterBrow is a user-owned conversational software foundry.

A user describes a tool they want through ordinary conversation. Iter clarifies
only consequential ambiguity, finds trustworthy and appropriately licensed
examples or patterns when useful, creates a versioned App Blueprint, builds the
tool in IterBrow's native tab/app style, proves that its real behavior works,
and opens it for the user. The user may continue requesting changes. Iter
updates the specification and implementation, preserves or explicitly migrates
the application's data, verifies the changed behavior, and either activates the
revision or restores the last healthy version.

The user owns the application's source, specification, tests, data, research
provenance, and revision history. An application may opt into durable native
cognition through named cognitive spaces, but ordinary application function
must not depend on an unrelated reasoning service being healthy.

## What this contract does not mean

- It is not a CRM generator. CRM is one later business-value demonstration.
- It is not satisfied by a prewritten app, screenshot, mockup, test helper, or
  narration that the app works.
- It is not satisfied by infrastructure completion without a user-visible tool.
- It does not require one physical AtomSpace, journal, reasoner, or socket.
- It does not authorize a distributed cognitive database project before the
  first working tool.
- It does not permit Codex to write or repair the feature code used to prove
  that Iter can build an unprepared application.

## Predictable execution protocol

1. **Intent checksum.** Before implementation, publish one paragraph stating
   what the user means and one paragraph stating the adjacent but incorrect
   interpretation. The user may correct either.
2. **Freeze observable examples.** Convert the accepted intention into
   Given/When/Then examples and assign the `BC-*` clauses they prove.
3. **External acceptance ownership.** The generic factory and candidate app
   cannot edit the contract, its verifier, or the acceptance fixtures used to
   judge them.
4. **Clause-bound work.** Every work unit identifies the contract clause,
   observed gap, proposed effect, fixed evidence, and rollback point it advances.
5. **No invisible completion.** Unit tests, architecture, atom counts, and
   internal commits are supporting evidence; none completes a clause requiring
   visible behavior.
6. **Amendment rather than reinterpretation.** New information may produce a
   proposed contract amendment. Only a human-approved new contract version may
   change an acceptance clause or non-goal.
7. **Stop on drift.** Work pauses when an action cannot be traced to an open
   clause, adds a new authority, or changes the product from general toolmaker
   to a specific application generator.

## Complete integrated demonstration boundary

The first demonstration uses the smallest complete working structure:

1. Generalize the existing APP-1/APP-2 seams from the hard-coded CRM application
   to manifest-registered user projects.
2. Give Iter one bounded factory tool that can validate a blueprint, create a
   user-owned project, record research provenance, stage source, and request
   activation through the existing quarantine/recovery path.
3. Let the user provide the first app request. Do not preselect or prewrite the
   proof application.
4. Require BC-01 through BC-08 plus BC-11 through BC-13 in the same real build
   and requested-revision trace. The builder uses named spaces, native governance
   and cumulative learning even when the app has no domain-reasoning feature.
5. Rehearse that complete experience and prove generality with a second category.

Physical sharding and additional reasoning engines are implementation choices;
the fabric interface is required now. CRM CSV/Mattermost value, future connectors,
reuse-first traceability, protected governor evolution and Mac installation remain
recorded obligations. Their implementation status must stay explicit.

## Existing capability and memory preservation

The user's 2026-09-22 clarification is additive: the foundry supports code Iter
builds, including managed self-repair, rather than defining a closed list of
permitted apps or languages. Existing tools, hot-loading, independently
supervised probation and exact rollback remain available. Build-action adapters
are extensible; a browser bundle format is not a universal source restriction.

Semantic memory and episodic continuity retain their owners, retrieval paths,
original identities and durable data. New personal/learning views connect to
those memories; they must not reset, fork or silently replace them. Existing
experience, history, recaps and tiered context remain inputs to building and
learning, alongside uniquely identified engineering evidence. Code activation
and rollback cannot erase what Iter learned. See Atlas INV-39.

## Human-selected first proof — 2026-09-23

The human selected CRM again to compare Iter's newly authored result with the
existing CRM control. This records the chosen proof application; it does not
amend the acceptance clauses or specialize the generic factory contract. Keep

and adopt useful ideas for a robust, useful result. The prior CSV intake and
source-grounded Mattermost brief requirements remain in scope through
CRM-1/MAGIC-1.

A copied or prewritten CRM, Codex feature repair, or installation alone cannot
establish the Iter-authorship proof. The selected project still requires actual
workflow use, durable data, a material human-requested revision, exact recovery,
and evidence that earlier outcomes affect a later native decision. The separate
second-category GENERALITY-1/BC-10 proof and all other retained commitments remain
open; selecting CRM does not waive them.

## Completion rule

This contract is not complete when the factory exists. It is complete only
after BC-01 through BC-13 have the applicable independent evidence. The first
integrated demonstration requires BC-01 through BC-08 and BC-11 through BC-13
for one unprepared app. BC-09 applies when the application requests domain
cognition; BC-10 proves generality before platform completion. Passing component
tests alone does not complete any clause requiring actual Iter use.
